# Fidelity

Daraja Local aims to behave like Daraja on the wire: the same routes, field names, error codes and callback shapes, quirks included, so code that works here works against Safaricom. This page says what matches, what doesn't, and how sure we are.

When Daraja Local and Safaricom disagree, Safaricom is right. If you find a difference, open an issue with a captured real response.

## How this was checked

On 2026-11-19 the same 26 requests were sent to the Daraja sandbox and to Daraja Local: successful requests and field errors for every API. After the fixes listed below, 25 matched exactly, apart from generated IDs. The other one was the sandbox answering `System is busy` that time. Those sync responses are now high confidence.

On 2026-11-20 a second run sent B2C, B2B, Account Balance, Transaction Status and Reversal requests with a correctly encrypted credential and collected every result through a public tunnel. All of them came back, but the sandbox's shared test initiator (`testapi`) was locked, so each one failed with `8006` `The security credential is locked.` That run confirmed the failure envelopes and the unknown-receipt codes below; successful result bodies are still unverified. C2B `registerurl` was down again (`500.003.1001` `Service is currently unreachable. Please try again later.`), and `simulate` was accepted but delivered nothing.

Before that, callbacks and results were checked less. The sandbox sent one STK callback, but no results for B2C, B2B, Account Balance, Transaction Status or Reversal requests made with an invalid credential. C2B URL registration was down (`500.003.1001` `Service is currently unreachable`), so C2B callbacks are still unchecked.

Everything else comes from Daraja documentation as reproduced in community SDKs, and from sandbox responses published in open-source repositories and tutorials. Confidence depends on the area:

- **OAuth and STK Push:** high. Many independent sources agree.
- **STK Push Query:** medium for a resolved request, lower for a pending or unknown one. Safaricom's documentation covers only the resolved case.
- **C2B response shapes and payloads:** medium. Samples differ between versions and sources.
- **Transaction Status and Reversal:** medium. Request fields and result shapes come from Safaricom's documentation, with a community SDK agreeing. Result value types differ between the two, and the "not found" case for Transaction Status is undocumented.
- **B2C request, acceptance and result shapes:** medium to high. Safaricom's v3 documentation and several SDKs agree. Error texts for individual fields, and the timeout body, are not documented.

Each known difference below says how sure we are.

## Captured from the sandbox

Each of these was seen in a real sandbox response on 2026-11-19, and Daraja Local now does the same. Confidence: high.

- **IDs.** `requestId`, `MerchantRequestID` and a generated `OriginatorConversationID` look like `104b-4235-9328-5de584002ffd785653`. `ConversationID` looks like `AG_20261119_01001003029wy0rrvtpn`. `CheckoutRequestID` is `ws_CO_`, then the date and time in Kenya time, one digit, and the phone without `254`: `ws_CO_191120260104173708374149`.
- **STK Push.**
  - A wrong password returns `500.001.1001` `Wrong credentials`.
  - A missing `CallBackURL` returns `400.002.02` `Bad Request - Invalid CallBackURL`.
  - A malformed `Timestamp` returns `Bad Request - Invalid Timestamp`, before the password is checked.
  - A decimal `Amount` such as `"1.5"` is accepted.
- **STK callback for a timeout.** `ResultCode` `1037`, `ResultDesc` `DS timeout user cannot be reached.`, with no `CallbackMetadata`. It was sent from `196.201.212.69` with `Content-Type: application/json;charset=UTF-8`.
- **STK Query of an unknown `CheckoutRequestID`.** HTTP 500, `500.001.1001`, `The transaction does not Exist`.
- **C2B field errors** use `400.003.02`, for both `registerurl` and `simulate`. A bad `ResponseType` says `Bad Request - Invalid ResponseType, Expected value is 'Completed' or 'Cancelled'`. The blocked-word text `Bad Request - Invalid ConfirmationURL - URL has the word MPESA` matched.
- **C2B `simulate`** replies with `OriginatorCoversationID`, `ResponseCode` and `ResponseDescription`, and no `ConversationID`.
- **B2C v3 field errors** add the `OriginatorConversationID` you sent, or `""`, to the usual error body.
- **Transaction Status field errors** use `400.002.02`, although Safaricom's documentation lists `400.003.02`.
- **Malformed JSON** returns `400.002.02` `Bad Request - `, with nothing after the dash.
- **OAuth.** `expires_in` is the string `"3599"`.
- **Unknown receipts.** Transaction Status answers `ResultCode` `2032` (a number), `The transaction receipt number does not exist.` Reversal answers `"R000002"` (a string), `The OriginalTransactionID is invalid.` Both report the unknown receipt even when the initiator can't be used, so the receipt is checked first. Captured 2026-11-20.
- **Result envelopes.** `ResultType` and `ResultCode` are numbers (Reversal's `R0000xx` codes aside). Balance, Status and Reversal results carry a placeholder `TransactionID` such as `UKK1000000`; B2C and B2B failures carry a receipt-like one. `ReferenceData` holds `QueueTimeoutURL` set to Safaricom's internal URL for B2C and Reversal, `Occasion` for Status, and for B2B a list of `BillReferenceNumber` (a number for a numeric reference), the internal `QueueTimeoutURL` and `Occassion`. Results come from `196.201.212.69` with `Content-Type: application/json;charset=UTF-8`. Captured 2026-11-20.
- **Earlier tokens stay valid.** On 2026-11-20 three tokens were requested in a row, and the oldest was still accepted afterwards. Safaricom's Authorization FAQ says "each request invalidates the previous token"; the sandbox doesn't do that, and production is unverified. Daraja Local keeps every token valid for its full lifetime, like the sandbox.

## What matches

- Routes: `GET /oauth/v1/generate`, `POST /mpesa/stkpush/v1/processrequest`, `POST /mpesa/stkpushquery/v1/query`, and C2B `registerurl` and `simulate` on `v1` and `v2`.
- Authentication: Basic auth for the token, then Bearer. The STK password is `base64(shortcode + passkey + timestamp)`.
- Request fields are JSON strings, including amounts and phone numbers.
- Error bodies: `requestId`, `errorCode`, `errorMessage`. Codes include `400.002.02`, `400.008.01`, `404.001.03` and `500.001.1001`.
- STK `ResultCode` values `0`, `1`, `1032`, `1037` and `2001`, and a callback with no `CallbackMetadata` on failure.
- STK Push Query answers a resolved request with `ResponseCode`, `ResponseDescription`, `MerchantRequestID`, `CheckoutRequestID`, `ResultCode` and `ResultDesc`, with `ResultCode` as a string.
- STK callback metadata types: `Amount`, `TransactionDate` (`yyyyMMddHHmmss`) and `PhoneNumber` are numbers, and `MpesaReceiptNumber` is a string.
- C2B `MSISDN` hides the number by registration version: SHA-256 hex for v1, masked for v2. Safaricom's C2B documentation and an independent SDK agree on this split. The v1 hash was also checked against a real sandbox sample and matched exactly.
- C2B routes exist on both `v1` and `v2`. Safaricom's current documentation lists the `v2` paths for `registerurl` and `simulate`.
- Registering again replaces the previous URLs, as Safaricom's documentation says the sandbox allows.
- URLs containing `mpesa`, `m-pesa`, `safaricom`, `exe`, `exec`, `cmd`, `sql` or `query`, in any case, are refused, per Safaricom's documented list.
- C2B `ResponseType` is the default action when your `ValidationURL` can't answer: `Completed` accepts, `Cancelled` rejects.
- B2C on `v1` and `v3`, with the documented request fields, the acceptance `Accept the service request successfully.`, and a result whose `ResultCode` is a number and whose `ResultParameters` keys match Safaricom's sample, including `TransactionCompletedDateTime` as `DD.MM.YYYY HH:MM:SS`.
- B2C failures arrive at `ResultURL` without `ResultParameters`, and a wrong `SecurityCredential` fails there with `2001` rather than in the synchronous reply.
- Transaction Status at `POST /mpesa/transactionstatus/v1/query` and Reversal at `POST /mpesa/reversal/v1/request`, with Safaricom's documented fields, the `RecieverIdentifierType` misspelling, and Reversal's `R000001` and `R000002` failures sent as strings while other codes are numbers.
- Quirks kept on purpose: Safaricom's `OriginatorCoversationID` typo and `ResultCode` as a string in C2B validation replies.

## Validation that is looser than Daraja

Daraja Local does not check these, and real Daraja may:

- STK `Timestamp` freshness. Only the format is checked.
- STK `TransactionType`, `PartyA`, `PartyB` and `AccountReference`.
- STK and C2B amount upper limits. Any whole number above zero passes.
- C2B `BillRefNumber`, which is passed through as given.

A `TransactionDesc` over 182 characters returns error code `1025` with a custom message. That code and text haven't been checked against Daraja.

## Emulator-only behavior

These exist because Daraja Local is a local tool, not because Daraja works this way:

- `simulate` fails until you've called `registerurl`. Real Daraja would silently have nowhere to deliver.
- Pending STK requests and access tokens live in memory, so a restart drops them.
- STK callbacks are retried up to 3 times, 1 second then 2 seconds apart, with a 10 second timeout per attempt. Real Safaricom's STK retry behavior is unverified.
- The dashboard's own API, including the endpoint that resolves an STK request, isn't part of Daraja and may change before 1.0.
- Daraja Local listens on `127.0.0.1` only, and never prunes the request log.

## Not implemented

B2C Account Top Up, Business to Pochi, Tax Remittance, Dynamic QR, Bill Manager and Ratiba (standing orders).
